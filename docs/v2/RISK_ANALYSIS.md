## Critical Risks (Severity 🔴)

### R7: Scope Creep

**Why it's #1:** This project has ambitious goals. The temptation to add "just one more feature" is the most dangerous risk.

**Mitigation Strategy:**
1. **Vision Freeze:** VISION.md is the constitution. If it's not in VISION.md, it doesn't ship.
2. **Feature Gate:** Every proposed feature must answer: "Does this serve the original mission?"
3. **Sprint Reviews:** End-of-sprint review against roadmap. Cut anything that slipped in.
4. **v2.5 Parking Lot:** Good ideas that aren't v2 scope go in the v2.5 backlog.

## High-Severity Risks (🟠)

### R1: LLM API Costs

**Estimated Token Usage Per Analysis Run:**

| Agent | Est. Tokens (input + output) | Est. Cost (GPT-4o) |
|---|---|---|
| BusinessDomainDetectionAgent | ~2,000 | $0.01 |
| BusinessObjectiveDetectionAgent | ~3,000 | $0.02 |
| KPIDiscoveryAgent | ~2,500 | $0.02 |
| InsightGenerationAgent | ~5,000 | $0.04 |
| ExecutiveReportAgent (summary) | ~4,000 | $0.03 |
| **Total per run** | **~16,500** | **~$0.12** |

**Mitigation:**
- Use GPT-4o-mini during development (~10x cheaper)
- Cache LLM responses keyed on prompt hash during development
- Token budget per agent (configurable in Settings)
- Rule-based fallback for every LLM agent

### R4: Data Cleaning Introduces Errors

**Mitigation:**
- Original data is always preserved as `raw_data`
- Every cleaning decision is logged with rationale
- Cleaning report shows before/after for every change
- User can review cleaning decisions in the report
- Conservative defaults: flag outliers, don't remove them

### R5: Report Quality

**Mitigation:**
- Design templates in HTML/CSS first (not generated by code)
- Use real executive reports as design references
- Jinja2 templates separate content from presentation
- Professional typography (system font stack, proper spacing)
- Iterate on real datasets during Sprint 4

### R11: Solo Developer Burnout

**Mitigation:**
- 1 buffer day per sprint (Friday)
- Sprint 6 is pure polish (no new features)
- If behind schedule: cut Web UI to minimal viable, prioritize core agents
- "Done is better than perfect" for v2.0; polish in v2.1

### R14: Test Coverage Drops

**Mitigation:**
- Tests written in the same sprint as the feature (not deferred)
- CI gate: no merge without passing tests
- Coverage tracking in each sprint review
- Target 85% not 100% — focus on critical paths

## Risk Response Plan

| If This Happens... | We Do This... |
|---|---|
| LLM costs exceed budget | Switch to GPT-4o-mini globally; increase rule-based fallback coverage |
| Domain detection fails on test dataset | Add domain-specific test cases; expand keyword dictionaries; manual override option |
| Cleaning removes important data | Add "conservative mode" flag; reduce auto-removal thresholds |
| LangGraph upgrade breaks graph | Pin to last working version; fork if necessary |
| Web UI takes too long | Ship v2.0 as CLI-only; add Web UI in v2.1 |
| Timeline slips past week 14 | Cut: PDF generation, parallel execution, 2 lowest-value agents |

## What We Deliberately Accept

These are known limitations we accept for v2.0:

| Limitation | Accepted Because |
|---|---|
| No database connectors | File-based keeps deployment simple. DB connectors are v2.5. |
| Max 1M rows | Covers 95% of analyst workloads. Larger datasets need different architecture. |
| No real-time streaming | Fundamentally different architecture. Out of scope. |
| No multi-user auth | Single-user tool for v2. Auth is v3. |
| No custom agent plugins | Plugin system is complex. Core agents cover 80% of use cases. |
| PDF may look slightly different across OS | WeasyPrint rendering varies. HTML is the primary format. |
